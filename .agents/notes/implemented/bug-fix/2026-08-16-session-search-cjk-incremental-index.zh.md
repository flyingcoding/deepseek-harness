# Agent Note: 增量会话搜索索引与中文子串支持

Status: implemented

[English](2026-08-16-session-search-cjk-incremental-index.md) | 中文

## 问题

`dsh web` 因 V8 堆耗尽而崩溃，工作区搜索对中文内容一无所获。每次 `searchSessions`/`searchEvents` 调用都会重新观测整个语料库：它会 `structuredClone` 每个活跃会话的全部事件，为每个事件构造一个搜索文档，重算整段日志的指纹，并对任何发生变化的会话全量重插文档。因此长会话让每次搜索的内存分配与整个语料库成正比，而一个巨大的命中文档还会在已满的堆上再物化数亿字节的字符串（`Array.from` 摘要路径与 `JSON.stringify` 指纹路径）。另一方面，FTS5 `unicode61` 会把连续的中文字符当成一个 token，而后端又把整个查询包成一个短语，因此多词查询和中文查询（例如在 `内存溢出` 里搜 `内存`）什么都匹配不到。

## 决策

[SQLite 会话查询提供方](../../../../packages/session-query/session-query-sqlite/README.zh.md)负责提取、协调和 schema 安全。本记录说明字面量 AND 查询、CJK 子串索引和有界查询保留。

SQLite 后端改为增量观测与增量索引。每个活跃 `Session` 在 WeakMap 缓存中持有一个增量 SHA-256 流、缓存的面层折叠结果，以及上次写入的指纹与事件 seq；事件深度冻结、公开快照数组在追加时整体替换，因此哈希流只会对自上次观测以来新追加的事件做哈希，指纹计算不再需要任何克隆。对账只为上次索引 seq 之后新追加的事件写文档，只更新新被遮蔽的旧文档（`surface = 'shadowed'`，分块 `IN` 列表），并且缓存记账只在事务提交之后应用。持久化日志通过持久化句柄读取，不再进行第二次事件克隆，文档在写入时插入索引；每份已加载来源在其行写入后释放。稳定观察仍会在事务开始前保留全部发生变化的冷来源，因此重建大型冷语料库仍可能占用大量内存。继承的观察缓存另行通过 `preparedSessionCacheSize` 限制保留的 Session 数量，并通过 `preparedSessionCacheMaxEvents` 限制逻辑事件数；活跃租约保持钉住。查询 SQL 用 `instr`/`substr` 把 `highlight()` 输出窗口化到首个命中标记附近，因此每行的 JavaScript 内存由摘要窗口而不是完整文档限定，`makeSnippet` 也在这个有界窗口上工作。

中文文本支持任意长度的搜索：每个中文连续段都以零宽空格分隔的 unigram+bigram token 流存储（模式版本 10 会在原地重置更早的派生索引），查询把其中的中文段展开为同样的 bigram（单字保留 unigram）。以空白分隔的查询词条作为独立加引号的字面量做 AND 匹配，调用方的 MATCH 语法始终是惰性数据，也不再要求相邻。摘要把 token 流解码回可读文本：完整的连续段从 unigram 前缀读回；窗口片段锚定在第一个被标记的 token 上，因此超长连续段的窗口从命中位置开始仍显示精确字符。无密钥 `session-query-cjk` 快照通过已发布的 headless profile 搜索固定时间的 Session 证据，并固定返回的原始中文文本。

对账的稳定性门禁（快照列表变化时重试）不再把活跃会话持有的修订号抖动视为不稳定：挂载中的会话其 write-behind 刷写会持续更新持久化文件，而它被索引的行本来就由 TEMP 覆盖层遮蔽，继续比较这些修订号只会不断重试进入下一次刷写，在重建耗时超过刷写间隔的语料库上让每次搜索都饿死。非活跃会话的快照抖动仍然会重试。

继承的批量标题读取默认最多并发读取一份持久化日志（`persistedReadConcurrency` 默认 1），减少相较四路并发读取时同时保留的冷日志。冷观察通过租约保留不可变切点，并在使用后淘汰超限且未被钉住的条目。`readSession` 和 `listEvents` 等整段日志精确读取保留上游的独立副本语义，仍会分配完整输出；增量搜索索引不改变这些保证。

## 曾考虑的替代方案

**FTS5 `trigram` 分词器。** 不予采纳，因为短于三个字符的查询——无论中文词（如 `内存`）还是拉丁 token（如 `AI`）——都会静默地一无所获。

**外部内容表或 contentless 表加独立原文表。** 不予采纳，因为 `highlight()` 定位会丢失或不可用，需要额外同步一张表并手写摘要匹配。

**保留每次搜索的全量重建，只修指纹字符串化。** 不予采纳，因为活跃长会话期间每次搜索的观测、克隆与重插仍是 O(语料库)，OOM 依然存在。

**复用会话内部增量维护的 `SurfaceManager`。** 不予采纳，因为引擎只能看到公开的会话 API；在每次快照变化时重放 `foldSurface` 成本低，且只依赖已导出的契约。

## 后果

每个可识别的更早版本派生索引会在下次打开时重置一次；派生索引本来就按可弃设计。中文索引文本大约翻倍，`match_count` 统计命中的 bigram 数量，因此多字中文查询的匹配计数相对拉丁 token 会偏高。极端情况下单一中文连续段文档的摘要会牺牲命中前的精确上下文（摘要锚定在命中处），而不是牺牲内存上限。拉丁子串行为不变（`AI` 仍不匹配 `BRAID`）；无密钥快照与两份 README 都记录了新的 AND 与中文语义。大体量语料库的批量标题读取现在是串行的，因此一次冷标题遍历比旧的 4 路并行更慢；日志规模较小的部署可以调高 `persistedReadConcurrency`。按契约返回整段日志的精确读取（`readSession`、`listEvents`）仍会分配完整输出，包括其 API 返回的独立事件副本。
